# Atuin 18.23.0 alignment — 2026-10-01

## Baseline and cause

The host's Home Manager Atuin client/daemon and the NixOS Atuin sync server are
owned by `nix-meta`. Its flake input was pinned to 18.18.1, while Pytuin's
development shell already supplied 18.23.0. A 18.23.0 status probe had
forward-migrated the user's real history database with migration
`20260818000000`; the 18.18.1 daemon then failed on startup because that
migration was absent from its resolved migration set. The active socket
continued accepting clients while systemd restarted the daemon.

Observed before deployment on 2026-10-01: `atuin-daemon.socket` was active at
`/run/user/1000/atuin.sock`; `atuin-daemon.service` repeatedly exited with
status 1, had 1,238 restarts, and invoked the old 18.18.1 store path. Both
Nix-evaluated Home Manager client and server package versions resolve to
18.23.0 after this change. No command modifies or replaces the history
database.

## Change

- Pin `inputs.atuin` to v18.23.0 and update `flake.lock` to release commit
  `78366dca8c4941731e06a2f81c0980cc2ccc3836`.
- Set both Home Manager package metadata overrides to 18.23.0. They keep the
  package selected by the client, daemon, shell initialization, PTY proxy, and
  server on one derivation/version.
- Enable Atuin's opt-in `output.enabled` setting so the daemon stores output for
  Atuin's native `atuin output` search; the latest release does not enable
  capture by default.
- Update the Atuin Codex hook compatibility comment. Its current payload
  normalization remains in place.
- Keep the existing Home Manager zsh initialization ordering: Atuin's
  `pty-proxy init zsh` is evaluated before atuout's hook, while the normal
  Atuin zsh history integration is emitted by nix-terminal. Both now resolve
  the pinned package through `programs.atuin.package`.

## Deployment regression and root cause

The operator activated the 18.23.0 system generation with:

```sh
sudo nixos-rebuild switch --flake /home/andrew/Documents/Projects/nix-meta#server
```

The generated `atuin.service` then failed with exit status 127 before Atuin
could construct its server configuration:

```text
error while loading shared libraries: libssl.so.3: cannot open shared object file
```

The failed package is `/nix/store/cvrbapll5l1abv4wvvs5r8a3cwrmzgxy-atuin`,
from `/nix/store/dvliwqzhqwvv2jc9giqkazz02vbw5x2p-atuin.drv`. Both `atuin`
and `atuin-server` declare `libssl.so.3` and `libcrypto.so.3` as `NEEDED`.
The client has an OpenSSL RUNPATH and resolves them; the server had an empty
RUNPATH and `ldd` reported both libraries as not found. OpenSSL 3.6.2 was in
the package closure, but closure membership does not add a path to the ELF
loader's search list.

The exact defect is in Atuin v18.23.0's official
[`atuin.nix`](https://github.com/atuinsh/atuin/blob/v18.23.0/atuin.nix): its
Linux `postFixup` adds the OpenSSL RUNPATH only to `$out/bin/atuin`. Cargo also
installs `$out/bin/atuin-server` from that source build, but the fixup omits it.
The release's [`flake.nix`](https://github.com/atuinsh/atuin/blob/v18.23.0/flake.nix)
exports that package directly. This explains why OpenSSL is a declared input
and closure reference while the server still fails at process load.

Pytuin's `nix/packages/atuin-18.23.0.nix` packages the official prebuilt GNU
client and server releases with `autoPatchelfHook`. Its output
`/nix/store/kc8i433y3q15pkfnnj71v1dwz19ymndz-atuin-18.23.0` runs both
binaries in a sanitized environment. Pytuin's server VM test exercises that
prebuilt package. `nix-meta` overrides the module with the official source
flake package, so the VM test did not execute the binary that was deployed.

## Selected repair and regression boundary

`nix/atuin-18.23.0.nix` now preserves upstream's existing fixup and appends a
server-specific `patchelf --add-rpath` using `lib.makeLibraryPath [ openssl ]`.
Both `profiles/terminal.nix` and `machines/server.nix` import that one helper,
so client, daemon, PTY proxy, shell integration, and sync server remain one
18.23.0 source-built derivation. No store path is hardcoded in the expression,
and no service or global `LD_LIBRARY_PATH` is used.

The repaired package is `/nix/store/lgrsznvmshn0km9js86w282wkx6iz280-atuin`,
from `/nix/store/nd4cdf4sz7q3cpypzy1xwrv018qfynw0-atuin.drv`. Its server
RUNPATH is `/nix/store/l0vl4dali2mvbpi30a8da1f71jl85myg-openssl-3.6.2/lib`;
`ldd` resolves both OpenSSL libraries, and sanitized execution reports:

```text
atuin 18.23.0 (NO_GIT)
atuin-server 18.23.0
```

The new `checks.x86_64-linux.atuin-server-runtime` reads the server and Home
Manager packages from the evaluated `server` configuration, asserts that their
output paths are identical, then executes both version commands with `env -i`.
This is the boundary that previously escaped coverage. The publish gate now
builds this check; a toplevel-only build remains insufficient because it does
not execute the server ELF.

Remove the local package fix when a pinned upstream Atuin package either adds
the required RUNPATH to every installed dynamically linked binary or stops
dynamically linking `atuin-server` to OpenSSL. The runtime check should remain.

## Alternatives considered

1. Appending the missing RUNPATH is the narrowest reproducible package-level
   repair and preserves the selected official source build.
2. Adding `autoPatchelfHook` and explicit OpenSSL inputs could repair every
   binary, but it is broader and overlaps upstream's existing client fixup.
3. Switching all consumers to Pytuin's verified prebuilt package would work,
   but changes package provenance and ownership during a focused repair.
4. A service-only library path would start systemd but leave the package broken
   for every other normal Nix execution. A global library path was rejected.
